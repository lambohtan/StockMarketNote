## 二、需要先对齐的四件事

### 2.1 关于"分析哪只有潜力"（需求 #3）

系统能做到的：
- 把每只票的**同一批指标**算出来并横向对比（增长、盈利质量、估值分位、趋势状态、机构与内部人动向）
- 按可解释的规则排序，你能点开看到每一分是怎么来的
- 用 LLM 把财报和电话会读完，提炼多空双方最强的论点

系统做不到的：**预测涨跌。**

这不是谦虚。上一份调研里提到的 FINSABER 研究（20 年、100+ 标的的系统回测）结论很明确：LLM 选股策略在长周期宽标的下没有稳定超额收益，且失败模式高度一致 —— 牛市过度保守，熊市过度激进。

所以"潜力"在这个系统里的定义是：**在一组可复核的标准下，这只票比池子里其他票更符合你的偏好。** 不是"它会涨"。

### 2.2 关于风险对冲推荐（需求 #4）—— 这条最有意思

这是四步：

**① 诊断你的真实风险**
- 行业分布（yfinance 提供 GICS sector）
- **有效持仓数** = 1 / Σwᵢ²（Herfindahl 倒数）。你名义上有 8 只票，有效可能只有 3.2 只 —— 这个数字通常很扎心
- 组合平均两两相关性
- 因子暴露：SPY beta、QQQ beta、利率敏感度（用 TLT / ^TNX 回归）
- **历史压力测试**：把你的组合放进 2022 加息年、2020 疫情崩盘、2018Q4 这几段，看会跌多少

**② 找出缺口**
对比 S&P 500 行业权重，你缺什么；以及一句话总结"你的组合最怕什么"（大概率是"利率上行 + 成长股杀估值"）

**③ 找候选**
在缺失行业里筛：与你**整个组合收益序列**的 250 日相关性最低、且基本面过关的票。每个候选明确写出"它在什么情况下能救你"。

**④ 算配比**
计算边际风险贡献 —— 加入 X% 的某只票，组合年化波动率从 A 降到 B、历史最大回撤从 C 降到 D。给区间，并明确标出代价。

#### 但必须说清楚三件事

1. **危机中相关性趋同。** 2020 年 3 月几乎所有股票一起跌。用不同行业的股票做对冲，在你最需要它的时候最不管用。真正的对冲是**不同资产类别** —— 债券、黄金、现金。系统会同时给你股票候选和资产类别选项，你自己权衡。

2. **分散降低波动，也降低上行。** 这笔钱你定位是风险资本、追求超额收益。把它分散到最低风险，等于直接违背你自己设的目标。

3. **所以正确的框架不是"把风险降到最低"，而是"确保你承担的是你想承担的那种风险"。** 报告的目标是让你看清自己在赌什么，而不是劝你少赌。

### 2.3 关于定时任务（需求 #6）—— 一个必须避开的坑

**你说的 cron job 在 Mac 上会静默失效。**

cron 是给不睡觉的服务器设计的。如果任务定在下午 6:30 而你的 Mac 那时候是合盖休眠状态，cron 直接跳过，不补跑，也不报错 —— 你会以为系统在跑，其实什么都没发生。

**launchd 的 `StartCalendarInterval` 不一样**：Mac 唤醒时内核更新系统时间，launchd 检查内部日程，发现休眠期间错过了任务就补跑一次。

所以：**用 launchd LaunchAgent，不用 cron。** 这也顺带解决了需求 #7（开机自启、崩溃重启由系统托管）。

### 2.4 关于 skill（需求 #9）

上一份调研里找到的：

- **[tradermonty/claude-trading-skills](https://github.com/tradermonty/claude-trading-skills)**（2.7k star，50+ skills）—— 最对口。其中 5 个不需要 API key
- [agiprolabs/claude-trading-skills](https://github.com/agiprolabs/claude-trading-skills)（67 个）
- [yennanliu/InvestSkill](https://github.com/yennanliu/InvestSkill)

**但要注意定位差异**：这些 skill 是给"你和 Claude 对话时"用的，是交互式的。你要的这个软件是**无人值守的定时任务**。两者不是替代关系：

- **软件**负责：每天定时抓数、算指标、扫异常、推送 → 这部分必须是确定性代码
- **skill**负责：你收到推送后，想深挖某只票时，在 Claude 里调用 → 交互式研究

我的建议是先把软件做出来，skill 作为"人工深挖"的补充，在 P4 阶段再评估哪几个真的有用。**先装 50 个 skill 不会让系统变好，只会让你分不清哪个在起作用。**

## 三、我建议加的（你邀请我想的）

### ⭐ 1. 信号有效性追踪 —— 最重要的一条

系统每天记录每个信号触发了哪些票，然后**自动跟踪这些票之后 30/60/90 天的表现**。

半年后你能直接回答：
> Reddit 热度信号推荐的票，60 天后平均涨跌多少？13F cluster 呢？Form 4 呢？内部人买入 + 技术回调同时触发的呢？

**这是让系统越用越聪明的唯一机制。** 没有它，你三年后还在用第一天拍脑袋定的权重。有了它，你可以砍掉证明没用的信号 —— 大概率会砍掉一半。

### ⭐ 2. 从第一天起存所有原始快照

这是**最容易忽略、后果最严重**的架构决策。

如果你不从 day 1 把每天的 Reddit 排名、Form 4 记录、价格、评分全部存进数据库，那么半年后你想验证任何模型，数据已经不存在了 —— ApeWisdom 不提供历史，Form 4 要重新爬。

存储成本：SQLite 单文件，一年几百 MB。**这个决定的成本几乎为零，但它决定了这个项目一年后是"能自我改进的系统"还是"一个每天发通知的玩具"。**

### 3. 影子组合（paper portfolio）
系统的推荐如果你全买了，现在值多少？和你实际操作对比。这是对系统最诚实的评估，也能告诉你：你的人工干预到底是加分还是减分。

### 4. 持有期与税务视角
追踪每个持仓的持有天数，接近 365 天时在报告里标注（长期 vs 短期资本利得税率差异对你很实在）。

### 5. 数据源健康监控
yfinance 是非官方接口，随时可能改。每次运行记录各数据源状态，连续失败就推送告警 —— 否则你会拿到静默的错误数据还以为一切正常。

### 6. 报告归档 + 全文检索
所有历史报告入库可搜。"我三个月前是怎么看这只票的" 是个高频问题。

## 四、软件架构

### 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **Python 3.11+** | 金融数据生态全在这（yfinance / edgartools / pandas） |
| 存储 | **SQLite** | 单文件、零运维、够快。这个数据量根本用不上 Postgres |
| Web | **FastAPI + Jinja2** | 轻，只监听 127.0.0.1。你是后端出身，不需要前端框架 |
| LLM | **LiteLLM** | 一套代码接 100+ 家，换模型改一行配置 |
| 调度 | **launchd** | 见 §2.3 |
| 推送 | **ntfy** | 免费、有 iOS app、一条 curl 就能发 |

### 目录结构

```
stockwatch/
├── core/
│   ├── sources/          # 数据源适配器，各自独立
│   │   ├── base.py       #   统一接口 + 健康状态上报
│   │   ├── prices.py     #   yfinance（可替换）
│   │   ├── edgar.py      #   8-K / Form4 / 13F
│   │   └── reddit.py     #   ApeWisdom
│   ├── store/            # SQLite，每日快照 + 迁移
│   ├── analysis/
│   │   ├── attribution.py   # 归因引擎
│   │   ├── health.py        # 恶化扫描（三级）
│   │   ├── portfolio.py     # 组合诊断、相关性、压力测试
│   │   ├── hedge.py         # 风险对冲推荐 + 配比  ← §2.2
│   │   ├── pool.py          # 股票池构建与排序
│   │   └── efficacy.py      # 信号有效性追踪  ← ⭐
│   ├── llm/              # LiteLLM 封装 + prompt 模板 + 成本记账
│   └── report/           # 报告生成（markdown / html / ntfy 短文本）
├── jobs/
│   └── daily.py          # launchd 每天调一次，跑完退出
├── web/
│   ├── app.py            # FastAPI：设置、上传 CSV、看历史报告
│   └── templates/
├── config.yaml
└── data/stockwatch.db
```

### 四个关键架构决策

**决策 1：一次性脚本 + launchd，不做常驻守护进程**
常驻进程要处理崩溃恢复、内存泄漏、日志轮转。一次性脚本跑完就退出，调度和重启交给系统。Web UI 是另一个独立的轻量常驻进程 —— 两者互不影响，任何一个挂了另一个照常工作。

**决策 2：所有数值计算用确定性代码，LLM 只做最后一公里**
指标、相关性、评分、异动检测 —— 全部是可复现的 Python。LLM 只负责两件事：读财报/新闻写摘要、把结构化结果翻译成人话。

这样换模型不影响任何数字，也不会因为幻觉出现错误的财务数据。**你的报告里每一个数字都能追溯到具体的计算，而不是"模型说的"。**

**决策 3：数据源适配器 + 健康上报**
每个源实现同一个接口。yfinance 哪天挂了，换 Alpha Vantage 只改一个文件。每次运行记录各源的成功/失败/延迟。

**决策 4：写入即快照，永不覆盖**
每天的原始数据带日期入库，只追加不更新。这是 §3.2 那条建议的技术落地。

### 数据模型（核心表）

```sql
positions(date, ticker, shares, cost_basis, market_value)   -- 每次上传 CSV 一份快照
prices(date, ticker, open, high, low, close, volume)
fundamentals(date, ticker, revenue_ttm, gross_margin, pe, ps, ...)
reddit_rank(date, ticker, mentions, upvotes, rank, mentions_24h_ago)
edgar_filings(filed_at, ticker, form, item_codes, url, summary)
signals(date, ticker, signal_type, score, payload_json)     -- 每个信号的触发记录

alerts(date, ticker, level, category, body_md)
reports(date, kind, body_md, ntfy_sent)
llm_calls(ts, model, tokens_in, tokens_out, cost_usd)
source_health(ts, source, ok, latency_ms, error)
```

## 五、实现顺序

每一期都独立可用，做完就能开始产生价值。

| 期 | 内容 | 产出 | 预估 |
|---|---|---|---|
| **P0** | 环境验证 | `tools/check_env.py` 在你 Mac 上跑通 | 今天 |
| **P1** | 数据底座 | SQLite + 数据源适配器 + 每日快照落库 + CSV 解析 | 1 周 |
| **P2** | 组合分析 | 需求 #1 —— 持仓体检、相关性、压力测试、有效持仓数 | 1 周 |
| **P3** | 自动化闭环 | 需求 #5#6#7 —— 归因 + 恶化提醒 + launchd + ntfy | 1–2 周 |
| **P4** | 股票池 | 需求 #2#3 —— 三源汇总 + 排序 + LLM 正反分析 | 2 周 |
| **P5** | 风险对冲 | 需求 #4 —— 诊断/缺口/候选/配比 | 1–2 周 |
| **P6** | Web UI | 需求 #10 —— 设置、上传、报告浏览 | 1 周 |
| **P7** | 自我改进 | ⭐ 信号有效性追踪 + 影子组合 | 1 周 |

**顺序说明：** P3 排在股票池之前，因为"每天自动告诉你持仓出了什么事"是这个系统最快见效的价值。P6 Web UI 放后面 —— 前期你直接改 `config.yaml` 更快，等功能稳定了再包界面。

## 六、下一步

在你的 Mac 上（不是这个沙箱）：

```bash
pip3 install yfinance edgartools requests pandas numpy litellm
cd <这个文件夹>/tools
# 打开 check_env.py，填上 SEC_IDENTITY（你的邮箱）和 NTFY_TOPIC（可选）
python3 check_env.py
```

把输出贴给我。它会实测每个数据源在你的网络环境下到底能不能用 —— 我这边的容器和 VM 都被限制了出网，测不了。

拿到结果后我们就知道架构里哪些能按计划走、哪些要换方案，然后开始 P1。
